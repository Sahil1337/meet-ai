# @meetai/retrieval — embeddings, indexing, search

**Owner:** unit 4, retrieval / RAG.

**Boundary:** propositions in, ranked proposition ids out. This package owns
the embedding client, the index, and the query path (hybrid search, fusion,
and — later, once the eval has a number to beat — routing and reranking). It
does not write prose: the answer is generated by `@meetai/ai` from evidence
the API hydrates using the ids you return.

## Layout

```
src/
  vectors.ts           cosine/dot/norm/normalize — pure, provider-free
  store/
    types.ts           VectorIndex: the index as this package sees it (package-private contract)
    pg.ts              openIndex(): Postgres + pgvector. The schema, BM25, the hybrid query
    sql.ts             the one driver behind the SQL: Bun.sql
  embedders/gemini.ts  GeminiEmbedder: works today, so the eval can run today
  embedder.ts          HttpEmbedder: the local embedding service. Still a stub
  indexer.ts           PropositionIndexer: claim text → vector, keyed by proposition id
  searcher.ts          HybridSearcher: query → ranked proposition ids
test/                  bun test — needs TEST_DATABASE_URL; skips without one
```

Working: the index, hybrid search, the Gemini embedder, measured by
`evals/retrieval`. Stubbed: `HttpEmbedder` (the self-hosted service). Not
started: query routing, reranking.

```bash
bun test                # from this directory or the repo root
bun run eval:retrieval  # from the root; needs GEMINI_API_KEY until HttpEmbedder exists
```

## Contracts

- Provides `Embedder`, `Indexer`, `Searcher` (`@meetai/core/src/contracts/retrieval.ts`).
- Consumes `Proposition` (only `id`, `text`, and the filterable fields:
  `type`, `speaker`, `meetingId`, `extractedAt`).
- Returns `SearchHit[]` — ids, scores, and `via` (which leg found it). The
  index is invisible to everyone else because of this: the API sees
  `Indexer` and `Searcher`, never a table.

## The index: Postgres + pgvector, two ways

The kickoff chose Postgres + pgvector over a dedicated vector database, and
this package now holds it to that. The SQL is written once and runs on two
drivers behind `openIndex()`:

| target | when | how |
| ------ | ---- | --- |
| `url` | everything: the API, the eval, the tests, production | a Postgres server with `CREATE EXTENSION vector`, over `Bun.sql` (built into Bun; no dependency). |

There is one target and it is required. An embedded driver (PGlite) used to
stand in for development and tests; it was removed because it gave every
machine its own private corpus — green tests and a working dev loop against a
database nobody else could see.

The schema is three tables, all prefixed `retrieval_`:

- `retrieval_index_meta` — one row: model, dimensions, schema version.
  Opening an index built with another model or width is an error, not a
  warning: a store queried with the wrong model returns confident nonsense.
  `openIndex({ reset: true })` (the eval's `EVAL_REINDEX=1`) is the way past
  it: drop and re-index.
- `retrieval_propositions` — id, text, `embedding vector(N)` under an HNSW
  cosine index, the filterable fields under btree indexes, and `doc_len`
  for BM25. `extracted_at` is kept as the ISO string it arrives as (core's
  rule: dates are strings); a generated `extracted_date` column makes the
  `from`/`to` filter indexable and keeps the old "compare the date part"
  semantics exactly.
- `retrieval_postings` — `(term, id, tf)`: the inverted index for BM25,
  filled from `unnest(to_tsvector('english', text))`. Postgres tokenizes,
  stems and drops stop words for documents and queries alike, so the two
  sides agree by construction.

Why not a dedicated engine (Qdrant, Weaviate, LanceDB): one more process on
the demo Mac, a second query language next to the SQL memory will need, and
nothing the eval could show for it at this corpus size. Why not SQLite +
sqlite-vec: FTS5 has BM25 built in, which is tempting, but the vector side
is a brute-force scan and Apple's SQLite build refuses extensions, so every
teammate would be swapping binaries. Postgres scales the vector side (HNSW)
and the keyword side (a btree on `term`) and is where memory is heading.

## Hybrid search, and what "correct" means here

`HybridSearcher` runs one SQL statement per query with two legs and a fusion
step, all inside the database:

1. **Filter first.** `SearchFilters` (types, speakers, meetings, date range)
   apply *inside each leg before its limit*, so `limit` counts records that
   qualify — not records that scored well and were then thrown away.
2. **Vector leg.** Top `candidates` by cosine over the HNSW index.
   `hnsw.ef_search` is raised to at least `candidates` for the query (HNSW
   returns at most `ef_search` rows — a classic silent truncation) and
   `hnsw.iterative_scan` is set so filtered queries are not short either.
3. **Keyword leg.** Top `candidates` by BM25 (k1 = 1.2, b = 0.75) over the
   postings table, with IDF from the whole corpus. It is real BM25, not
   `ts_rank`: `ts_rank` has no IDF, and on this corpus the rare word
   ("Tejasva", "pgvector") *is* the signal.
4. **Fusion.** Reciprocal rank fusion (reading list B3), `k = 60`, per-leg
   weights default 1 and 1. A record found by both legs scores higher than
   one found by either; that is the whole idea.
5. **The floor is on cosine, in every mode.** `minScore` drops any hit whose
   cosine to the query is below it, even one the keyword leg ranked first —
   every hit carries a cosine for exactly this reason. Cosine is the only
   score here with a stable meaning across corpora; BM25 and RRF are relative
   to the result list. The floor is what makes "the corpus cannot answer
   that" possible, and it is tuned against the out-of-domain queries in the
   eval, which pass only when *nothing* clears it.

`via` on each hit says which leg found it (`vector`, `keyword`, or `hybrid`
for both), so the eval can attribute every hit. `mode: "vector" | "keyword"`
exists to run one leg alone under the same admission rule; the eval runs
all three and prints them side by side.

What hybrid does *not* do: it cannot surface a record the vector leg rates
below the floor, however exact the keyword match. That is deliberate. If
the eval shows exact-name questions failing that way, the fix is a lower
floor for hits confirmed by both legs — a knob to add with a number, not
before.

## Scaling notes

- HNSW build defaults (`m = 16`, `ef_construction = 64`) are fine to a few
  million rows; raise `ef_search` per query for recall, not `m`.
- Postings grow at roughly ten rows per proposition. The BM25 leg touches
  one btree range per query term; stop words never reach it.
- `upsert` is one transaction per batch of 100 (the indexer's batch size).
  Re-indexing a meeting is idempotent by id.
- pgvector's HNSW indexes up to 2000 dimensions; `openIndex` refuses wider.
  768 is the measured sweet spot anyway (below).
- One index holds one project's claims by construction — `Proposition`
  carries no project id, so `SearchQuery.projectId` is accepted and not
  enforced. Adding `projectId` to `Proposition` (a core PR) turns that into
  a column and a filter; nothing else moves.

## First tasks

1. Run `bun run eval:retrieval` with a key and put the three-mode table
   below. Every change after is judged against it.
2. Tune `EVAL_MIN_SCORE` against the out-of-domain queries.
3. Stand up the embedding service (with unit 1) and implement `HttpEmbedder`
   against it, replacing Gemini. Same interface, so only the container
   changes — but re-index: vectors from two models are not comparable.
4. Query routing: structured questions ("who owns X") → `SearchFilters` on
   `type`/`speaker`; semantic → hybrid.
5. Reranking, once step 1 gives a number to beat.

## Prior findings (Sep 2026, Gemini `gemini-embedding-001`, removed scratch scripts)

Measured before the self-hosting decision; the *method* transfers to whatever
local model is chosen, the numbers do not.

- Default output was 3072-d and unit-length. Cross-lingual was strong (a
  Hindi translation of the probe scored 0.97, above both English paraphrases).
- Retrieval put the right doc at rank 1 on all three test queries with a wide
  margin (e.g. 0.81 vs 0.58), including one with almost no lexical overlap.
- Dimension sweep — the *gap* between related and unrelated is what matters,
  not the top score:

  | dims | bytes/vec | related | unrelated | gap |
  | ---- | --------- | ------- | --------- | --- |
  | 128  | 512       | 0.9051  | 0.8282    | 0.08 |
  | 768  | 3072      | 0.8042  | 0.6874    | 0.12 |
  | 1536 | 6144      | 0.8024  | 0.6856    | 0.12 |
  | 3072 | 12288     | 0.8223  | 0.7124    | 0.11 |

  768-d was the sweet spot: a quarter the storage of 3072-d with no loss of
  separation; 128-d nearly collapsed the gap.
- **Task type is asymmetric.** Index documents as documents and embed the
  question as a query. The same sentence under the two task types only scored
  ~0.83 against itself, so mixing them costs real recall. This is why
  `Embedder.embed` takes `kind`.
- **Truncated vectors must be renormalized** before cosine. Models trained
  with Matryoshka representation learning return unit-length vectors only at
  full dimension.
- **Similarity thresholds are not comparable across dimensions.** Re-tune any
  hard-coded threshold when the dimension changes.
- Reading list: `docs/rag-reading-list.md` (A1 Dense X for the unit, A5 MTEB
  for the model — sort by the Retrieval column, B3 RRF for fusion).
